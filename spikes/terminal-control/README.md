# Terminal-rendering spike

Throwaway/evaluation code — **not** part of the `VMware.CloudFoundation.InstanceRecovery` module and excluded from PSGallery publishing (see `.github/workflows/release.yml`'s `$remove` list).

## Why this exists

We're building a WPF orchestrator that spawns existing interactive PowerShell/PowerCLI cmdlets, unmodified, via a Windows ConPTY pseudoconsole so prompts, colors, tables, and `Write-Progress` render exactly as they would in a native console. The open question was which terminal-rendering approach to embed in WPF. This folder has two small, side-by-side prototypes to compare against identical output, rather than guessing:

- **EasyTerminalSpike** — uses [EasyWindowsTerminalControl](https://github.com/mitchcapper/EasyWindowsTerminalControl), which wraps the real Windows Terminal native rendering engine. It owns its own ConPTY spawning internally via `StartupCommandLine` — it does **not** use the `ConPty/` project in this folder.
- **VtNetCoreSpike** — uses [VtNetCore](https://github.com/darrenstarr/VtNetCore) (a pure C# VT100/xterm parser) plus a hand-written WPF `DrawingContext` renderer (`TerminalRenderer.cs`), driven by our own `ConPty/` class library (ported from [Microsoft's official ConPTY sample](https://github.com/microsoft/terminal/tree/main/samples/ConPTY/GUIConsole)).

Both spike apps launch `pwsh.exe -NoLogo -NoExit`; run `test-render.ps1` inside each (it's copied next to the built exe) to compare colors, `Format-Table` alignment, in-place `Write-Progress` updates, and `Read-Host` prompts side by side.

This can only be built and run on Windows — it was written on macOS and has not been compiled or executed. Build it, run both, and report back what you actually see so we can pick a rendering approach for the real orchestrator.

## Known risks to check first

- **EasyWindowsTerminalControl**: its own README describes the WPF flavor as "not yet publicly packaged" and dependent on beta Windows Terminal packages, even though NuGet lists a `1.0.38` release targeting `net8.0-windows7.0`. Its own sample app (`TermExample`) instead targets `net10.0-windows10.0.26100.0` with `RuntimeIdentifier win-x64` via a project reference to the source, not the NuGet package. **If `dotnet restore`/`build` fails on `net8.0-windows7.0`**, edit `EasyTerminalSpike.csproj` to match that TFM/RID combination instead (see the comment already in the file).
- **VtNetCore**: the NuGet package (`VtNetCore`, `1.0.30`) was **unlisted by its owner** — last published 2019, no longer actively maintained. Unlisting hides it from search but a pinned-version restore should still work. **If restore fails**, vendor the library's source directly (it's small — just the `VtNetCore/` folder in its repo) into `VtNetCoreSpike/` instead of referencing the package.
- `TerminalControl.Spikes.sln` was hand-written, not generated by Visual Studio/`dotnet new sln`. If it doesn't load cleanly, regenerate it:
  ```
  dotnet new sln -n TerminalControl.Spikes
  dotnet sln add ConPty/ConPty.csproj EasyTerminalSpike/EasyTerminalSpike.csproj VtNetCoreSpike/VtNetCoreSpike.csproj
  ```

## Build & run

```powershell
cd spikes/terminal-control
dotnet build TerminalControl.Spikes.sln

dotnet run --project EasyTerminalSpike
dotnet run --project VtNetCoreSpike
```

In each running window's embedded console, run:

```powershell
.\test-render.ps1
```

## What to look for

| Check | EasyTerminalSpike | VtNetCoreSpike |
|---|---|---|
| Foreground/background colors render correctly | | |
| `Format-Table` columns stay aligned | | |
| `Write-Progress` bar updates in place (doesn't scroll a new line per tick) | | |
| `Read-Host` prompt works, typed input echoes correctly | | |
| Arrow keys / Ctrl+C behave as expected | | |
| Resizing the window reflows/rescales cleanly | | |
| Actually builds & restores without extra setup | | |

`VtNetCoreSpike/TerminalRenderer.cs` intentionally does **not** draw the text cursor (blinking caret) — `VtNetCore`'s `TerminalCursorState`/`TextPosition` field names weren't verified against actual rendered behavior, so it was left out rather than guessed at. Note in your comparison if its absence is actually noticeable during the `Read-Host` prompts.
